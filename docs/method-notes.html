3D Wind Rose Method Notes

What this tool computes, and — the part that matters most when you cite it — what it does not. It bins recorded climate data into a 16-direction frequency table and draws it: no building enters that calculation, and loading a different model does not change a single frequency, calm percentage or monthly figure. Everything below is read from the source code or computed from it, not from what a wind-rose tool is generally assumed to do. Where the code makes something unclear, this page says so rather than inferring.

Audience Architecture students and staff Method EPW frequency binning · no flow solved Runs Entirely in the browser Version 1.0.0 · 15 September 2026

Three things to know before you cite a number

  1. The rose is the weather station's climate, not the site's wind. EPW wind speed is a 10 m open-country measurement at the station. Checked directly against the source: no height, terrain or roughness correction, and no displacement adjustment, exists anywhere in the code. So the rose describes the regional climate the station recorded, not the wind arriving at a particular building's façade. Use it to compare directions and seasons, not to read off a design wind speed.
  2. Calm is excluded from the petals — but not from the denominator. Records below 0.5 m/s are counted as calm and never placed in a direction/speed cell. But the percentage each cell shows is still divided by every record the table was built from, calm hours included. So the petals of a rose with, say, 8.3% calm sum to 91.7%, not 100%. Quote the calm percentage alongside any reading from the petals, or the figures will not reconcile for anyone checking your working.
  3. The wind data and the map location can be two different places — and "Sheffield" is Doncaster Airport. The built-in Sheffield preset is recorded at Doncaster Sheffield Airport (WMO 034054); the tool's own label already says so — "Sheffield (Doncaster Airport)", not bare "Sheffield" — but the parenthesis is easy to read past. More generally, the tool tracks the distance between where the loaded wind data came from and wherever the map is currently centred, and warns once that gap passes 50 km. Loading a preset and then moving the pin — or the reverse — is the situation to watch for.
01

What it computes

A frequency table, binned once from whichever EPW records are loaded, drawn as a stack of coloured wedges. Nothing else. The building shown beside the rose plays no part in the calculation — js/epw.js and js/windrose.js, the two files that produce every number the rose shows, take a plain list of {direction, speed, month} records and nothing else; neither file contains any reference to a building, a model or a footprint. Loading a different .obj changes how large the rose is drawn (see How exact the numbers are) and nothing about what it says.

PropertyValue in the code
Direction sectors16, 22.5° each
Sector assignmentMath.round(direction ÷ 22.5) mod 16
Speed bins0–2, 2–4, 4–6, 6–8, 8+ m/s — 5 bins, top bin open-ended
Calm thresholdspeed < 0.5 m/s
Frequency formula(count in cell ÷ total records) × 100
 Math.round, not Math.floor, in the sector assignment: sector 0 spans 348.75°–11.25°, centred on due north, rather than 0°–22.5°. Every sector is centred on its compass point the same way.

The frequency total, and what it leaves out

Each cell's percentage is divided by every record the table was built from — calm hours included — even though calm records are excluded from the sectors themselves. Summed across all 16 sectors and 5 bins, the petals therefore add up to 100 minus the calm percentage, not to 100. See the first trap above for what that means when quoting a figure.

Monthly breakdown

Records are grouped by the EPW file's own month field (1–12) and each month's group is passed through the same binning function independently: a month's percentages are a share of that month's own hours, not a share of the year. Records with a missing or out-of-range month still count towards the annual table but not towards any month.

What the interface reports

Alongside the rose, the sidebar shows the total hours behind the currently displayed table (annual, or a single month) and the calm percentage for that same table — both read straight from the binning function's own output, not recomputed separately.

02

The data

EPW parsing

An EPW file's first 8 lines are header metadata; the parser skips them and reads one hourly record per remaining line. Wind direction is column 21 (index 20 of the comma-split line); wind speed is column 22 (index 21) — the parser's own comment cites the EnergyPlus Weather File (EPW) Data Dictionary for the full column layout, and the indices it reads match it. A speed of 999 or above is EnergyPlus's own missing-data sentinel, and such rows are dropped rather than treated as a real reading. The month is read from column 2. If no row survives these checks, the parser refuses the file outright rather than returning an empty table.

The embedded presets

Three UK locations are built into the tool, so the sidebar's "suggested locations" list loads a wind rose instantly with no file to download. All three are binned from real recorded TMYx EPW files of 8,760 hourly observations each, including a genuine month-by-month breakdown:

Computed by the author, not read from the code (see Limitations of this page): the great-circle distance from Doncaster Sheffield Airport (53.48°N, 1.01°W) to Sheffield's Town Hall (53.38°N, 1.47°W), using the tool's own distance formula, is about 32 km. The airport sits in the lowland Don valley at roughly 9 m elevation; the city centre sits at roughly 60 m with the Peak District immediately to its west — the preset is climatologically, not just geographically, removed from most Sheffield sites.

TMYx stands for a typical meteorological year, extended series. It is not a record of any single real year: it is assembled by selecting, for each calendar month, the most statistically representative month from many years of observation at that station, then stitching the twelve together. No date inside a TMYx file corresponds to weather that actually occurred on that date — treat it as a representative year, not a historical one.

04

How exact the numbers are

Unlike a solver, there is no approximation in the arithmetic itself: a frequency percentage is a count divided by a total, computed once and read straight into the rose. The honest treatment is therefore different — the question is not precision, it is representativeness: what a correctly counted number from this particular source can and cannot tell you.

What limits the result anyway

Four things, independent of each other. The source year: a TMYx file is a synthesised representative year, not any year that occurred — see The data. The 22.5° sector: two real peaks 15° apart are drawn as one. The five speed bins, with an open top: nothing distinguishes a 9 m/s hour from a 20 m/s hour — both fall in "8+". The station itself: a 10 m open-country reading with no height, roughness or terrain correction applied anywhere in the code, so it describes the regional climate the station recorded, not the wind arriving at any particular building's façade.

The rose's drawn size is not a fifth kind of precision — it is not data at all

Checked directly in rebuildWindRose(): the rose's inner radius, its overall span, and even its petal thickness are all set from the loaded model's footprint (or a fixed default footprint when nothing is loaded), and the whole drawing is then rescaled so the tallest direction's stack always reaches the same span. Two roses are therefore never comparable by their size on screen — a small-looking rose over a large building and a large-looking rose over a small one can show identical wind climates. Only the proportions within one rose — which direction is tallest, how the bins stack — carry any information at all.

What a student may and may not quote

  • May: the prevailing direction, and how the petal proportions change between two months or two locations.
  • May: the calm percentage, quoted alongside any petal reading (see the first trap).
  • May not: a wind speed at a building, read off the rose as if it were measured there — the source never leaves the weather station.
  • May not: a comfort or shelter claim of any kind — the tool computes none, see What is and isn't modelled.
  • May not: the rose's size on screen, as evidence of anything — it is auto-scaled to the building's footprint, not to the data.

06

Three exercises

Each teaches one principle using only the built-in presets — no upload needed — and takes ten to fifteen minutes.

Exercise 01

The prevailing direction moves with the seasons

  1. Load the London preset.
  2. Set the Month slider to January and note which direction has the tallest stack.
  3. Move it to July and note the tallest direction again.
  4. Switch back to All Year and compare both months against the annual shape.

Principle. The annual rose is an average of twelve different climates, and no single month necessarily resembles it. A façade opened for summer ventilation on the annual prevailing direction may face entirely the wrong way for infiltration and heat loss in January. Read the month you actually care about, not just "All Year".

Exercise 02

A rose cannot tell you where a building is sheltered

  1. Load any preset, then import an .obj model — or leave the default placeholder footprint in place.
  2. Note the rose's shape and size.
  3. Change the Scale slider from 100% to 250%, then back down to 50%.
  4. Watch the rose while you do it.

Principle. The rose's size changes with the building's footprint; its shape — the only part that carries data — does not move at all, because nothing about the geometry enters the binning. A rose has no idea a building is even present, so it cannot show downwash, channelling, wake or shelter of any kind. Reading those needs a flow tool — this tool's own sister application, Urban Wind Lab, solves exactly that, on the explicit condition of accepting its own, quite different, set of caveats.

Exercise 03

The commonest direction is not the windiest one

  1. Load the Edinburgh preset, All Year.
  2. Find the direction with the tallest total stack — the most frequent direction.
  3. Look instead at which direction has the largest share sitting in the 6–8 and 8+ bins specifically.
  4. Compare the two directions.

Principle. Frequency and energy are different quantities. A direction that blows often but gently can carry less total wind than one that blows rarely but hard — wind's momentum scales with the square of its speed, so a less frequent high-speed direction can matter more for structural loading or driving rain than the direction the petals make look dominant at a glance. The rose shows frequency directly; it takes a second look to find energy.

Limitations of this page

The sections above describe the tool. This one describes the document.

Where each number came from

The Sheffield distance is the one figure on this page computed from an external reference point, and it is labelled as such rather than presented as read from the code.

What this page deliberately does not do

It applies no meteorological correction of its own. Where the tool leaves EPW data uncorrected for height, roughness or terrain, this page reports that gap; it does not fill it with a worked example, because doing so would imply the tool performs a correction it does not.

A gap the provenance rule leaves

The reference list in the footer names the EPW format and TMYx as the code's own terms. It does not, and cannot, name whichever sources actually informed the EPW parser or the embedded presets while the tool was built — the code does not say, and this page will not guess. The Sheffield-to-city-centre distance in The data is a different kind of gap: it is this page's own arithmetic, using a reference coordinate (Sheffield Town Hall) the code itself does not contain. The coordinates for both points are given alongside the figure, so the calculation can be checked or redone independently rather than taken on trust.

How the references were checked, and the limit on that

Each entry was looked up against a named, citable source rather than recalled from memory. Identifying details — ISBN, version tag, release date — are given on an entry wherever they could be confirmed. One detail could not be pinned to a single version: TMYx's own citation page states a different year in different places (2019, 2022 and 2026 all appear); the entry below gives the year as read and says so, rather than presenting one as settled.

And the tool itself is unvalidated

No comparison against a published wind rose for the same station exists in the tool or anywhere behind it — checked directly: no such comparison, benchmark or reference dataset appears anywhere in the source.

The tool is not self-contained

The source embeds a MapTiler API key as a plain string in js/main.js, and the running tool makes network requests to MapTiler for both map tiles and location search — visible to anyone who views the page's source. This is a real limitation of the artefact, stated neutrally: it is not a single self-contained file the way its sister tool is. The tool does still function without a working key or without network access at all — confirmed directly: after 6 seconds without a loaded map style, the code falls back to a blank, valid style, and the building and wind rose render fully; only the satellite/street imagery underneath is missing.

Everything on this page was read from the tool's source code or computed from it; Limitations of this page says which figures are which, and by what method. Where a figure would have needed a value the code does not contain, it was removed, or clearly marked as the author's own calculation rather than presented as read from the source.

For a wind statement that must inform a real design decision, correct the data for height and terrain before using it, and bring in a flow tool or a wind engineer for anything involving a building's response to that wind. This tool is built to teach what a wind rose is and how one is built from recorded data — nothing more, and it says so throughout.
